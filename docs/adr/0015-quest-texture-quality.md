# ADR 0015: Quest texture quality is a config key and an in-game control, applied by GOT hooks

Status: accepted, implemented (`src/quest/sentinel/texture_quality.h`, `texture_quality_hook.{h,cpp}`, `sysprop_int_share.h`, #943; the in-game control and the live apply: `texture_menu.{h,cpp}`, `texture_menu_hook.{h,cpp}`, #1012, #1186). On in every Quest build; the default level is `stock`, which serves the runtime's own size.
Not yet observed on a headset: the "Prediction" sections are what the first run must show. The procedure for the run, and the thresholds that decide the default, are in `docs/testing/quest-texture-quality-headset-sheet.md`.

## Context

The community installer's patcher (EchoTools/echoApkPatch, by marshmallow-mia, for EVRCE) offers a Graphics Patch setting for the Quest APK. It changes the size of the buffer the game renders each eye into. This repository's Quest build repacks the APK with a shim and does not ship a patched `libr15.so`, so the setting has to come from the runtime. Only facts about the game are used from the patch repository (the setting's name, its levels and the absolute per-eye sizes); no code or bytes are.

What the game does (pinned `libr15.so`, build id `b243509c08ce677aeb95fa348016949b3fc45230`; `src/quest/sentinel/pinned_targets.h`):

- `CVR::RefreshRTSize` (ELF `0x1a709a0`) asks the headset runtime for the suggested eye-buffer size with `vrapi_GetSystemPropertyInt` property id 5 (width, call at `0x1a709f4`) and id 6 (height, `0x1a70a04`), multiplies each by `CustomViewportScale` (1.0 unless a script sets it) and stores the pair.
- `CVR::Resize` (`0x1a70d0c`) creates the swap chain from the pair, once per process, and logs `Creating OVR swap chain with size %i x %i (2 slices, %u sample[s])`.
- `vrapi_GetSystemPropertyInt` is a `JUMP_SLOT` in libr15 at ELF `0x36fa728`; libr15 is `BIND_NOW`.

## Decision

A config key, `graphics.texture_quality`, read from the Quest `config.yaml` (`src/quest/sentinel/quest_config.cpp`). Values: `stock`, `very_low`, `low`, `medium`, `high`, `very_high`, `ultra`, lower case. The default (key absent) is `stock`: no hook, the runtime's own size. `texture_quality.h` holds the default (`kDefaultLevel`) and, separately, the level every mistake gives (`kFallbackLevel`, always `stock`).

One GOT hook on the `vrapi_GetSystemPropertyInt` slot, installed at every level. The handler calls the original with the game's own arguments every time and returns its answer, except for property ids 5 and 6 when the *applied* level is not `stock`: those return the level's width or height for the headset the runtime's own answer to the same call names (`HeadsetForStockSize`: a stock size of 1680 or more is a Quest 3, below it a Quest 2). Every other id returns exactly what the runtime answered. At `stock` the game gets the runtime's own size.

| level | Quest 3 width x height | Quest 2 width x height |
| --- | --- | --- |
| very_low | 1344 x 1408 | 1152 x 1264 |
| low (the stock size) | 1680 x 1760 | 1440 x 1584 |
| medium | 2376 x 2568 | 1728 x 1904 |
| high | 3072 x 3380 | 2016 x 2224 |
| very_high | 3584 x 3944 | 2304 x 2528 |
| ultra | 4096 x 4506 | 2592 x 2848 |

The sizes are the absolute per-eye sizes of EchoTools/echoApkPatch's Texture Resolution setting (graphics v9, `native/texres/texres.c` at `8aa27ecdc`, by marshmallow-mia); the Quest 3 column is what #943 shipped. Nothing here measured any headset's native size. Samples stay at 2. The sizes are per headset because a Quest 2 at the Quest 3 table renders about 4.5 times its stock pixels at `high` (#943, #1012).

The configuration's level is latched by the first install in the process (a second install with another level is refused and logged). It is the *start* level: the player's saved choice replaces it at the first eye-size query (below), and from then on the applied level changes only through the live apply. A change of the key takes effect at the next launch; the key is read once.

### The control and the live apply (#1012, #1186)

The design is marshmallow-mia's (EchoTools/echoApkPatch, graphics v9 and v10: the "Texture Resolution" control and the level that applies while the game runs). Only facts about the game were taken from it; every function was read in ReVault (the Quest libr15) and is hooked through a GOT slot libr15 calls it by, so no code byte is written (ADR 0021). `texture_menu_hook.h` lists the five hooks, their slots and the evidence; `pinned_targets.h` holds the pins.

What a player meets:

- The game's settings menu has a GRAPHICS page with one control, "Texture Resolution", of six entries in the menu's order: Very Low, Low, Medium, High, Very High, Ultra. The default entry is Low (the headset's stock size), or the level the key names.
- A change applies at the next rendered frame, with no restart. The game logs a new `Creating OVR swap chain with size W x H` line with the level's size for the headset.
- The choice is remembered in `nevr_texture_quality.json` (`{"menu_index":N}`), a file of ours beside the game's settings, written after the player changes the control and read back at the next launch before the swap chain is made. The game's own saved slot (`msaa` in `settings_mp_v2_quest.json`) is not read: a settings file that never held the setting reads 0, which is Very Low, and cannot tell a choice from a default. A player who never chose starts at the default, Low (or the level the key names).
- Sizes are per headset (the table above); a Quest 2 never gets a Quest 3 size.

How: the control rides on the setting `graphics|msaa` (`SR15GfxSettings+0x1c`). `ApplyRuntimeGfxSettings` sets the render's MSAA mode from two constants (both 2 in the store build) and reads that field only for a log line, so the field can carry the level. The quest sections of `gamesettings_config.json` hide the setting and its page "GRAPHICS (1/3)", and `menu_settings.json` lists a three-entry "Anti-aliasing" row on that page. `CJson::DecodeFrom(CFileSp const&, uint)` reads each file, strips its comments and parses the text with `CJson::DecodeFrom(char const*, unsigned long long)`; two GOT hooks rewrite the two documents in memory between the read and the parse (`texture_menu.cpp`, by structure, never by a stored copy; a document of another shape is passed through and logged). `ValidateGfxSettings` clamps the field to 0..2, so its hook puts the value the settings held back, clamped to 0..5. `ApplyRuntimeGfxSettings` is where the game delivers its settings (boot and every change): its hook asks for the level the field holds. `CEngine::CheckForResize` runs once per rendered frame on the render thread (`RenderBefore`): its hook runs the original and, when a level other than the applied one was asked for, the engine's own rebuild in the order the engine needs: `CVR::RefreshRTSize` (the eye-size hook answers it with the new level, so the render-target manager is built at it), then `CEngine::Resize` through the engine's resize slot with the display the engine keeps, which flushes the GPU and recreates the swap chain, the render targets and the pass framebuffers.

The log line the game writes for the msaa field indexes a three-entry name table. In the pinned libr15 the table (`kMsaaNames`, ELF `0x3690278`) is followed by `R_AARCH64_ABS64` relocations to valid pointers (`0x3690290`, `0x3690298`, `0x36902a0`), so for an index of 3 to 5 the call prints a wrong word and cannot fault. It is left alone: clamping the field around the call would show the settings component a wrong index while it refreshes the control.

The applied level is the level the buffers are built for; the eye-size hook answers it. A request (the menu, or the development property `debug.nevr.texture_level`, a level word or an index 0..5 set from adb) changes no answer; only the apply commits a level, on the render thread, right before it rebuilds.

The key and the control. The saved value wins: at the first eye-size query (before the game delivers its settings) the sentinel reads the saved index from the settings file (`CSysInfo::GetLocalAppDataDirectory`, then the `"%s/RAD/LoneEcho/%s"` path libr15 builds). With nothing saved, the key's level starts, and the game's first delivery of its settings is changed to it so the control shows it and the next save keeps it; with the key absent (`stock`) nothing is changed and the control shows Low.

What the apply waits for and what it refuses. It waits for the engine's ready flag and for the VR layer to be initialised and not display-lost (the same tests `CheckForResize` makes). It refuses for good, and logs why, when the engine's resize slot is not `CEngine::Resize`, when a game function does not match its pin, or when `RefreshRTSize` did not ask the runtime (the stored size override, below): the level then applies at the next launch. A rebuild the engine reports as failed is undone (the previous level, the engine rebuilt at it) and the failed level is not asked for again. Two levels that give the same eye size (`stock` and Low on one headset) are committed without a rebuild.

Logging. Nothing on the game's call path logs. A poller thread writes `texture_quality_start` (the start level and where it came from), `texture_menu_json` (each document: rewritten, not JSON or a shape mismatch, with the counts), `texture_quality_request` (each request, its source), `texture_quality_applied` (each change of the applied level, with the size and the engine's result) and the two error lines `texture_quality_apply_refused` and `texture_quality_apply_failed`, each with its consequence. Thirteen counters (`gfx_check_calls`, `gfx_live_applies`, `gfx_menu_deliveries` and the rest) carry the rest.

Any mistake in the key gives `stock`, never the default and never `high`, with one Warning that names the key (`quest_config.cpp`, `config file key=graphics.texture_quality rejected reason=<why> (falls back to stock; ...)`). The reasons: `unknown_level` (a word that is not one of the six: wrong case, a number, empty; the word is named when it is short printable ASCII), `not_a_word` (a mapping, a list, or the key with no value), `graphics_not_a_mapping` (`graphics: ultra`, `graphics: [ultra]`), `unset_variable` (a bare `${VAR}` that is not set) and `file_rejected` (the file is unusable as a whole, so it says nothing about this key). The fall back is separate from the default so that raising the default cannot turn a typo into the level that costs the most. A key under `graphics` other than `texture_quality` (`texture_qualty`, `Texture_Quality`) is one Warning that names it (`reason=unknown_key name=<key>`; the first eight, then one line counting the rest) and changes nothing else: the level is the default, as for an absent key, so a misspelling is heard instead of silently giving the default.

### Known path: a stored size skips the query

`CVR::RefreshRTSize` queries ids 5 and 6 only when the stored override pair at ELF `0x37a33e8` is zero. `CVR::SetRTSizeOverride` is the only writer found. Whether a Quest run sets it is not known: static reading finds one caller, `ConfigureEngine` (`bl` at ELF `0x11f3db8`), behind a flag test, passing 1920x1080. Where the game stores a size, it never asks the runtime and the key has no effect. This is a static reading of the pinned library, not observed on a headset; the first Quest run shows the swap-chain line either way.

The handler never logs on the game's call path. The install logs one line, whatever the level and the outcome (`texture_quality`, fields `result`, `quality`, `source`, `w`, `h`; `quality` and not `level`, because the log line's own `level` is its severity). Counters `gfx_native_eye_width` and `gfx_native_eye_height` carry the runtime's last answer to ids 5 and 6, which is the headset's native size, and `gfx_eye_size_served` counts the answers replaced.

### Why the PC loader accepts the section

The Quest reads the same `config.yaml` through the PC's `nevr_config` (`src/core/nevr_config.cpp`), which rejects a file with an unknown top-level key as a whole. A key under an existing section would have put render quality under a name that means something else (`diagnostics`, `social`); a new section keeps the key where it belongs, and the PC accepts `graphics` and reads nothing from it, as it does for `diagnostics`.

### The shared slot

`GotHook` allows one owner per slot, and the hardware dump (ADR 0006) already records every `vrapi_GetSystemPropertyInt` query. Two hooks on one slot would be refused. The texture-quality hook installs first (`src/quest/integration/ctor_sequence.cpp`) and marks the slot owned (`sysprop_int_share.h`); the dump then registers an observer instead of installing, and the handler tells it each query's id and the runtime's own answer (before any override). The dump therefore keeps recording what the runtime said, not what the game was told, and reports the slot as `shared`. When the texture-quality hook installs nothing (a refusal), the dump installs its own hook as before.

### Reference build input (#1737 C4)

The live libr15 is one of two builds. In the stock build `CVR::RefreshRTSize` (ELF `0x1a709a0`, 43 words) calls `vrapi_GetSystemPropertyInt` at words 21 (`0x1a709f4`, id 5) and 25 (`0x1a70a04`, id 6) through the PLT stub. In the reference build (the community's libr15 with a cave) both words are `bl 0x1a84890`, a cave that never calls the runtime and reads its own level from `settings_mp_v2_quest.json`. The vrapi hook above never sees those queries on that build, so the eye size would not follow the applied level.

`src/quest/sentinel/refresh_eye_size.h` classifies the live body from its bytes: every word other than the two sites must equal the stock body, each site must be the stock call or the `bl` to the cave, and the cave's first word must be `0xa9bc67f8`. Any other body is `unknown` and nothing installs. Only on the reference body is a second GOT hook installed, on the `RefreshRTSize` slot (`JUMP_SLOT 0x36dbd10`). Its handler reconstructs the stock body: it reads `CustomViewportScale(0)`, takes the stored override pair (`0x37a33e8`) when it is non-zero, and otherwise asks the runtime for ids 5 and 6 through the PLT stub, so the vrapi hook answers them with the applied level on both inputs. It stores the pair at `0x37a33e0` with the game's own truncation. It never calls the original on the normal path.

The reference input's start level is his rule, reconstructed from the cave: the `msaa` index V in the settings file (digit within the first 24 bytes after the key, read up to 15359 bytes, clamped to 0..4), at level `kLow + V`, default V=2 (High). The rule applies only on the reference input, only when the configuration is `stock` and the player has no marker. Its result is queued as the player's marker so the next launch reads it there. The `stock` input never uses it.

Consequences, on the record: a reference-input build with no configuration and no marker starts at High, not Low. The `kLow + V` mapping is the cave's index, not a claim about the size tables. The `refresh` field on the `texture_quality` install line says whether the second hook is in place.

## Prediction (written before a headset run)

The control (#1012). In the sentinel log, in this order: `texture_menu_install result=installed` (five statuses `ok`), `texture_quality_start` (`source=config`, or `player_marker` after a choice), `texture_menu_json document=menu_settings result=rewritten rows=1 pages=1` and `document=gamesettings_config result=rewritten rows=1 pages=1`. The settings menu shows a GRAPHICS page with one control, "Texture Resolution", of six entries, on Low. Choosing High on a Quest 3 logs `texture_quality_request source=menu from=low to=high`, then, within a frame, the game's `Creating OVR swap chain with size 3072 x 3380 (2 slices, 2 sample[s])` and `texture_quality_applied from=low to=high w=3072 h=3380 rc=0`; the picture fills the frame (no old-size corner, no black remainder). On a Quest 2 the same choice gives `2016 x 2224`. The sentinel logs `texture_quality_saved result=written quality=high menu_index=3`. After a restart it logs `texture_quality_start source=player_marker quality=high` and the first swap-chain line is the High size. `gfx_check_calls` grows at the frame rate. What would prove it wrong: no `texture_menu_json` line (the documents do not arrive through the two reads), `shape_mismatch` (the documents have another shape), a swap-chain line that does not follow a choice (the apply was refused: `texture_quality_apply_refused` names why), an old-size corner or a black picture after a change (the order, another thread, or a resource sized outside the engine's cycle), a crash on a change, a player who never chose starting anywhere but the default (`texture_quality_start source=config`), a choice that reads back as another entry, a `texture_quality_saved result=write_failed` line, or a settings menu that still shows the stock graphics rows.

The key alone (#943). Default (no `graphics` section): a `texture_quality` line `result=installed quality=stock source=default`, and the runtime's own size in the game's `Creating OVR swap chain` line. With `high`: `result=installed quality=high source=config w=0 h=0 sizes=per_headset`, and then `Creating OVR swap chain with size 3072 x 3380 (2 slices, 2 sample[s])` on a Quest 3 or `2016 x 2224` on a Quest 2. With `very_low`: `1344 x 1408` on a Quest 3, `1152 x 1264` on a Quest 2. With `low`: the runtime's own size, which is `1680 x 1760` or `1440 x 1584`. With `stock`: `result=installed quality=stock`, and the runtime's own size in the game's line. The counters `gfx_native_eye_width` and `gfx_native_eye_height` show the native size at every level.

What would prove it wrong: the swap-chain line shows a size other than the level's (the game reads the size somewhere other than ids 5 and 6, or creates the swap chain before the hook installs); no `texture_quality` line; a crash or a blank frame at `ultra` (GPU memory).

## Not claimed

That the Quest 2 sizes work on a headset: they are the patch repository's values, measured there on a Quest 3 only (its `UPDATE.md`, Graphics v10), and `high` and `ultra` cost frame time and GPU memory on either headset; this is why the default is `stock`. The default becomes `high` (one line, `kDefaultLevel`, and the test that pins it) after a Quest 2 has been run at `high` and its frame time and memory measured. The native sizes of the Quest 2 and Quest 3 are not measured here (the counters above measure them on the first run); a level defined as a scale of the native size is tracked separately (#953). That `low` is the installer's own number, not one derived from the other levels. That GPU memory suffices at `ultra`, on either headset: a rebuild at a lower level keeps the allocator's high-water mark (the patch repository measured 480 MB fresh at Low, 1190 MB fresh at Ultra and about 1190 MB after Ultra back to Low, on a Quest 3). That the live apply is safe on a Quest 2, in a match, or while a second thread calls `RefreshRTSize` (`ApplyRuntimeGfxSettings` does when the VR layer is up; which thread each runs on is not shown here). That the compositor has released the swap chain the rebuild destroys. That `CGAutoExposureCS` and the particle and decal buffers follow the rebuild (the patch repository found the first unused and has not verified a match). The value the store build saved under `msaa` before this build: the control reads it back as a level. The PC build already has the control this key would be: its own graphics settings carry a render scale (`resolutionscale`), MSAA (`msaa`), a quality level (`qualitylevel`, with a custom sub-struct that has a `textures` field), read by `ApplyRuntimeGfxSettings` at `0x140c31870` in `echovr.exe` and written back to the settings JSON by `fcn.140c2e8c0` (`0x140c2e8c0`) and `fcn.140c2e610` (`0x140c2e610`). The PC key is therefore not added: the game's own setting is the PC control, and it is a scale, not a level table (#956).
