# ADR 0028: game-derived content packs live on the CDN and in the signed manifest, never on a release page; they ship off

Status: proposed. Tracking issue: #1585 (the installer's fetch and placement, and what it does not yet cover). Builds on ADR 0012 (the nevr root), ADR 0019 decision 8 (a plugin carries no game-derived bytes)
and ADR 0023 (the manifest chain and its artifact kinds). Nothing in this record is built when it is written; "What is not known" lists
what no measurement covers.

## Requirement

A mod that changes the game's data (EchoCombat's gear is the first) reaches players and server hosts with nEVR, and:

1. **No game-derived byte is published by this repository.** A pack is built from a stock install's manifests and carries rewritten
   game assets; it is hosted on `evr.echo.taxi` and listed in the signed manifest, and nowhere else.
2. **Nothing changes for a player who did not ask.** A pack ships inactive. Installing one never splits a player from a stock server.
3. **Nothing unverified is applied.** A consumer applies a pack only when the manifest names it (sha256, size), its path is
   `packs/<name>`, and the player's own stock manifests hash to the values the pack was built from.

## Decision

1. **Where a pack lives.** The `content-pack` artifact kind (`docs/reference/verifying-a-release.md`, Step 8): platform
   `windows-x86_64`, name `<id>-<first 12 hex of sha256>.zip`, path `packs/<name>`, a `content_pack` object (`id`, `version`,
   `requires_stock_manifest_sha256` as a sorted list of one or two hashes, `stock_data_version`, `plugins`). The release-signer
   writes it (`put-content-pack`, carried forward per id on a publish). A consumer that does not handle the kind skips it.
2. **Where a pack never lives.** Not on a GitHub release page, not in the Windows zip, and not as a workflow artifact of a public
   repository (anyone with an account can download one). `tools/package_release.py seal` refuses any file outside its list and any
   directory in the tree; `tools/tests/test_release_assets.py` pins the upload globs of every release workflow. RELEASING.md,
   "Game-derived packages", states the rule.
3. **How a pack is built.** In a private job, from the PC stock data fetched by manifest, by the pack builder. The job hands the
   release-signer a file and its sha256. No third-party tool runs on a maintainer's machine; the plugins below build in CI.
4. **Plugins.** A plugin that carries no game bytes may be a public workflow artifact. EchoCombat's three plugins need MSVC (SEH
   `__try/__except`) and Microsoft Detours, which MinGW cannot build, so `.github/workflows/echocombat-plugins.yml` is the one
   Windows-runner workflow: hand-started, no secrets, a workflow artifact only, attested. The pack zip carries those plugin
   files next to the content, so a pack and its plugins have one version and one hash. `PowerBoost.ini`, the PowerBoost plugin's
   tuning file, is generated by EchoCombat's own tools from its gun-patch data by tools the public plugin workflow does not run
   (it only compiles), so the private pack job makes it and it travels in the pack zip.
5. **Off by default.** A pack serves nothing until the host's `config.yaml` lists its serving plugin with `args: {"active": "<id>"}`
   (`docs/reference/content-packs.md`, "Load early"). The installer fetches and places a pack; it never writes that line. A server
   host or a player who wants the pack adds it. A client with a pack active needs a server that has it (the pack changes game data,
   so a stock server and a pack client disagree).
6. **One pack at a time.** A pack's manifest replaces a stock manifest whole (`content-packs.md`, "Not covered"); two packs that
   change one set need a merged manifest, which nothing makes.

## Consequences

- The zip, the release page and the public workflow artifacts contain no game bytes, so a takedown or a licence question touches the
  CDN object and the manifest line only.
- A consumer cannot learn from the manifest whether `requires_stock_manifest_sha256` is true; it compares the values with the
  player's own install before it applies anything. The release notes state it as a claim.
- A plugin in the pack is unsigned (the release-signer does not sign plugins yet). Under `-require-signed-plugins` it does not load
  (AGENTS.md N147).

## What is not known

- The serving plugin's paths and the pack plugins' logs. `NvrContentOverlay` 1.1.0, built from commit
  309e2196029250729c8e349b92bfcb1eda9f682b of its repository (the `overlay` job of `.github/workflows/echocombat-plugins.yml`),
  reads a pack from `<root>\content\<id>` (content_overlay.cpp:264 in that repository), the folder `content\` that
  `src/core/nevr_root.h` (`kContent`) and ADR 0012 name. It writes its log to `<root>\plugin_logs\NvrContentOverlay`
  (content_overlay.cpp:162-171), and EchoCombat's three plugins write `<exe dir>\plugin_logs\<name>` (EchoCombat's plugin/nevr_plugin.h,
  function `EchoCombatLogPath`). Neither follows the house convention: a plugin writes no log file of its own and logs through the host's
  `ctx->log` into the run log under `<root>\logs` (`docs/standards/logging.md`, Rule 15). No `plugin_logs` folder is added to the root.
  The standing rule (AGENTS.md, "The game folder") allows nothing of ours in the game folder but `BugSplat64.dll`, so the three
  EchoCombat logs are a defect against it until those plugins move to `ctx->log`.

- The stock inputs of the private build job. The pack is pinned to the PC data (`_data/<data_version>/rad15/win10`: the two
  stock manifests and their packages). The signed manifest's `game-data` kind lists `android-arm64` data only
  (`_data/<data_version>/rad15/android`), which cannot stand in for it. The job fetches the PC data by manifest, so a PC
  `game-data` artifact (written by the release-signer) has to exist before a pack can be built.
- Whether the pack builder needs the stock package files as well as the manifests: the repack code links them and stats them
  (EchoCombat's vendored EvrFile manifest/repack.go, function `QuickRepack`); the first private run settles it.
- What a stock server does with VeilNet's UDP hello packets (the plugin sends one every 2 seconds and relays only to clients that
  said hello): not measured.
- A two-client match with a pack active has not been run.
