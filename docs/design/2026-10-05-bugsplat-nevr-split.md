# Design and Test Plan: Stable BugSplat Bootstrap + `nevr.dll`

Date: 2026-10-05
Status: implementation in progress; steps 1-2 landed (PE contract, ABI descriptor, attach proof-gate harness); proof gate passes under Wine, native Windows not yet run — no runtime source has moved

## Goal

Keep `BugSplat64.dll` as the stable filename and compatibility/bootstrap layer Echo VR loads, while moving the frequently changing NEVR feature runtime to `nevr.dll`. Preserve early runtime hooks and the game-facing import surface. Keep an actual minimal minidump path in `BugSplat64.dll`, usable after `nevr.dll` is absent or incompatible, as well as bounded bootstrap diagnostics. Do not modify Nakama, tag, release, or deploy.

## Evidence inspected

- The installed v34.4.631547.1 `echovr.exe` at `/mnt/games/cache/echovr-34.4.631547.1/bin/win10/echovr.exe` statically imports nine **named** `MiniDmpSender` methods from `BugSplat64.dll`; `objdump -p` shows no ordinal imports. The names are exactly the nine decorated names in `src/runtime/exports.def:10-19`. The replacement also reserves ordinal 1 for `DetoursExportPlaceholder`.
- The stock `BugSplat64.dll` has 43 named exports. The replacement currently has 26 exported symbols (including ordinal 1); the complete replacement export inventory is: `DetoursExportPlaceholder` (ordinal 1), `?setDefaultUserDescription@MiniDmpSender@@QEAAXPEB_W@Z`, `?setDefaultUserName@MiniDmpSender@@QEAAXPEB_W@Z`, `?setFlags@MiniDmpSender@@QEAA_NK@Z`, `?getFlags@MiniDmpSender@@QEBAKXZ`, `?createReport@MiniDmpSender@@QEAAXPEAU_EXCEPTION_POINTERS@@@Z`, `??1MiniDmpSender@@UEAA@XZ`, `??0MiniDmpSender@@QEAA@PEB_W000K@Z`, `?resetAppIdentifier@MiniDmpSender@@QEAAXPEB_W@Z`, `?sendAdditionalFile@MiniDmpSender@@QEAAXPEB_W@Z`, `MiniDumpWriteDump`, `NEVR_DeregisterResourceOverrides`, `NEVR_GetUPnPConfig`, `NEVR_RegisterResourceOverride`, `NEVR_ResetResourceOverrides`, `NEVR_ScheduleReturnToLobby`, `NEVR_SetGameModule`, `TokenAuth_GetDiscordId`, `TokenAuth_GetToken`, `TokenAuth_GetUsername`, `platform_compat_ApiVersion`, `platform_compat_Init`, `platform_compat_Shutdown`, `token_auth_ApiVersion`, `token_auth_Init`, and `token_auth_Shutdown`. Keep all 26 names and ordinal 1 stable in the first split, with exact signatures/calling conventions. Audit repository call sites, plugins, packaging and public headers for every export before assigning it to the host or forwarding it. The three TokenAuth functions registered in `boot.cpp` are internal module-proc names; determine whether they are also externally consumed before treating them as public ABI. Keep the full stock export surface out of scope unless a real caller is found.
- `MiniDumpWriteDump` in the current DLL loads system `dbgcore.dll` from the Windows system directory and forwards the call (`src/runtime/lifecycle/dllmain.cpp:24-57`). ReVault reports no static `MiniDumpWriteDump` import/caller in `echovr.exe`. The game's `HandleCrashDump` (`echovr.exe` VA `0x1401cefe0`) instead loads `dbghelp.dll` and resolves `MiniDumpWriteDump` dynamically. Keep the compatibility export, but do not mistake it for NEVR's full crash path.
- Full NEVR crash records, VEH handling and recovery hooks currently live in `src/runtime/lifecycle/crash_recovery.cpp`; the initialization path installs them (`src/runtime/lifecycle/initialize.cpp:377-394`). A small export wrapper alone would not preserve this behavior. ReVault evidence identifies `CrashExceptionFilter` at `0x1401cef00` as the registered game unhandled-exception filter. Its startup registration path calls `SetUnhandledExceptionFilter` before entering the game's main wrapper; that wrapper reaches `PreprocessCommandLine` later. ReVault decompilation of `HandleCrashDump` at `0x1401cefe0` shows it loads `dbghelp.dll`, resolves `MiniDumpWriteDump` (line 295), constructs `MiniDmpSender` (line 769), and calls `createReport` with the exception pointers (line 793). Therefore the stable shim's primary minimal dump path is the `BugSplat_createReport` export, not ownership of the replaceable Windows filter slot, and dbghelp is already loaded before this game callback even if it precedes NEVR's first Preprocess rendezvous. The shim records its own module directory and fixed crash-path candidates during attach; in `createReport`, it obtains the already-loaded dbghelp module with `GetModuleHandleW` and resolves the function without loading a DLL, then writes a valid dump. If the module/function is unexpectedly absent or a preferred directory is unwritable, try the next precomputed destination and write a fixed-size text diagnostic only after all dump destinations fail. Use an atomic reentrancy guard that is cleared when the callback returns, so nested reporting is suppressed but later recovered server crashes can still be captured. No NEVR logger, locks, heap-owned path state, or runtime load is allowed in the callback. The child-process harness must fault after the game filter is installed but before Preprocess, and prove the shim dump works. Do not promise capture for faults that bypass this game callback unless a separate, tested fallback is added. The game also writes its own dump, but that does not prove the shim's dump works.
- The game statically loads `BugSplat64.dll` before `WinMain` (`src/runtime/CMakeLists.txt:1-3`). In direct-import mode, `DllMain` currently calls `InitializeGameModule` synchronously on process attach (`src/runtime/lifecycle/dllmain.cpp:84-90`). In launcher mode, the exported `NEVR_SetGameModule` is called after loading the DLL (`dllmain.cpp:76-80`). Some file/module work is already deferred because it can deadlock under the loader lock (`src/runtime/lifecycle/boot.cpp:155-174`, `initialize.cpp:399-400`).
- The current target is a 30,471,264-byte `BugSplat64.dll`; distribution, the lite package, client test launcher, install guide and packaging verifier currently assume one runtime DLL (`CMakeLists.txt:275-305,358-378`, `tools/build_distribution.py`, `launch-client.sh`, `docs/beta/INSTALL.md`).
- The August 2 fold of `platform_compat` and `token_auth` into the monolith was to prevent separately required modules from being omitted. This split therefore needs pair/version checks and package/install tests, not independent optional DLL loading.

## Proposed architecture

### `BugSplat64.dll`: stable host

- Retain the nine imported BugSplat method stubs, ordinal-1 `DetoursExportPlaceholder`, `MiniDumpWriteDump` system forwarding, `NEVR_SetGameModule`, and all supported NEVR/plugin cross-DLL exports. Keep signatures and calling conventions fixed; implement NEVR exports as null-safe wrappers through a validated function table.
- Own the minimal early-start bridge, minidump callback, and bounded bootstrap/crash diagnostic record. The emergency path uses fixed storage and crash-safe OS writes; it must not depend on NEVR's logger, heap-owned path state, locks, or a loaded runtime.
- Keep the fixed image-base behavior required by the game/render stack (`src/runtime/CMakeLists.txt:234-240`).
- Do not statically import or PE-forward `nevr.dll` exports: either creates an eager dependency that prevents the shim from loading when the runtime is absent.

### `nevr.dll`: changing runtime

- Move current `PATCHES_SOURCES` and runtime-specific dependencies, including networking, game/server hooks, auth, plugins, telemetry, and detailed crash-recovery instrumentation, into a DLL with a no-op `DllMain`.
- Expose one versioned C entry point returning an API descriptor (`abi_major`, `abi_minor`, `struct_size`, and function pointers). The host validates the major version, minimum descriptor size and required entries before calling anything. Do not pass C++ classes, STL, exceptions, or allocator-owned objects across this boundary.
- Keep the module loaded for process lifetime while its hooks/callbacks may execute. Do not `FreeLibrary` a live runtime or call thread-joining shutdown paths from process detach.
- Load only the sibling file resolved from the recorded `BugSplat64.dll` module path, using `LoadLibraryExW` with DLL-load-directory and System32 search flags. Record the full path, Win32 error, expected/actual ABI version, and degraded action in a host-owned diagnostic record.

### Early bootstrap without doing the full runtime under the loader lock

- In direct game-import mode, the host's `DllMain` validates the executable and installs only a small detour on the already-used `PreprocessCommandLine` entry point. It does not load `nevr.dll` or call the full runtime there.
- On the first `PreprocessCommandLine` call, after process attach has returned, the host loads `nevr.dll`, validates the API, and calls the runtime's `preprocess_before` dispatch before forwarding to the game's original function. The runtime sets its game-instance pointer and runs `PreflightRuntimeBootstrap()`, which parses `-server` and sets NEVR mode globals before the original call. The host then calls the original exactly once, passes its result to `preprocess_after`, and returns the original result. The post phase rechecks `-server` and invokes the existing idempotent `RunDeferredRuntimeBootstrap(...)` after original preprocessing; clients skip this server-only path. This preserves current semantics in `boot.cpp:56-70,139-150,176-188`; the original function does not set NEVR's `g_isServer`. The host supplies the original trampoline through the C ABI so the runtime does not install a second detour on the rendezvous address.
- If image validation, the host detour, runtime loading, API validation, or initialization fails, write a stable diagnostic, call the original game function when it is safe to do so, and leave the shim crash path active. Do not fall back to loading the runtime from `DllMain`.
- `NEVR_SetGameModule` is retained as an external compatibility entry point. No in-repository caller was found in the inspected launcher or runtime sources; therefore launcher-mode initialization is an external contract to preserve and test with a dedicated ABI harness, not an existing repository path that may be claimed as proven.
- The bootstrap diagnostic record uses a fixed buffer and one bounded `WriteFile` append to `%LOCALAPPDATA%\EchoVR\logs\nevr-bootstrap.jsonl`, with `%TEMP%\EchoVR\logs` as fallback if the environment path is missing or unwritable. DllMain copies `%LOCALAPPDATA%`, `%TEMP%`, and the shim module directory values into fixed buffers with bounded environment/path APIs; it performs no directory creation or file I/O. After attach, reporting creates directories and tries destinations in that order. Diagnostic failures do not recurse into NEVR logging or block startup. DllMain records only fixed-memory status; any deferred reporting mechanism is triggered after attach returns.
- Crash-dump destinations are precomputed in fixed buffers: `%LOCALAPPDATA%\EchoVR\crashes`, then `%TEMP%\EchoVR\crashes`, then the shim directory. The `BugSplat_createReport` callback creates the first two directories on demand and tries each in order, opening a unique per-process/per-crash `.dmp`; failure at an install directory must not prevent the writable `%LOCALAPPDATA%` or `%TEMP%` attempt. The harness makes the shim directory unwritable and verifies that a valid dump lands in the configured fallback. No heap-owned path state is used.
- Proof gate (must pass before migrating any runtime source): build an isolated startup harness that invokes the exact proposed host DLL's `DLL_PROCESS_ATTACH` path with MinHook and the `PreprocessCommandLine` detour, records attach return and runtime-load/API/init timestamps, and verifies no runtime operation occurs before attach returns. Run it under both Wine and native Windows; stress startup with another process thread and verify no attach hang, loader-lock inversion, or partially installed detour. Verify the hook precedes the original function, preserves every argument/result, and calls runtime preflight and original exactly once, including concurrent/reentrant entry and runtime load/API/init failures. Test the supported game timestamp `0x6452dff6` and target base+`0x116720` with prologue validation. MinHook's heap setup and thread enumeration/freezing in this path are explicit risks; a harness that only proves a later hook fires is insufficient. If attach-time MinHook cannot pass these checks, stop and redesign the rendezvous before moving runtime code. Host and runtime hook ownership must use separate MinHook state/instances or a proven serialized shared manager, with disjoint targets; the runtime must never install a second hook on this rendezvous address. Finally confirm ordering in the nested client run.

## Implementation sequence

1. Add PE import/export contract checks and a minimal shim/runtime ABI harness before changing target ownership.
2. Establish and run the attach-time MinHook proof-gate harness before moving any runtime source. It must cover Wine and native Windows, loader progress, event order, concurrent/reentrant hook entry and exact argument/result preservation. If it fails, stop and revise the rendezvous design.
3. Implement host diagnostics, host-owned minidump capture from the proven `BugSplat_createReport` callback, the versioned C ABI and runtime load/validation state machine. Cover absent, incompatible, missing-entry, dependency-load and init-failure cases. The crash harness must exercise the same callback with the runtime unavailable both after filter registration but before Preprocess and after runtime-load/API/init failure; parse/validate the resulting minidump header/signature and confirm it contains the deliberate faulting process/thread. Make the shim directory unwritable and prove the `%LOCALAPPDATA%` or `%TEMP%` fallback contains the valid dump. If in-process dbghelp fails or deadlocks in this harness, stop and design/test an out-of-process writer before continuing.
4. Establish and test the early `PreprocessCommandLine` rendezvous and the external `NEVR_SetGameModule` compatibility path. The ABI test asserts `preprocess_before -> original once -> preprocess_after` ordering; server tests prove preflight sets NEVR server globals before original parsing and deferred bootstrap runs afterward only when `-server` is present, with its current command-line recheck and idempotence; client tests prove the server-only post-bootstrap is skipped. Preserve exact one-call behavior and original trampoline semantics.
5. Split CMake targets: `BugSplat64` owns only host/compatibility/bootstrap/crash code; `nevr` owns the existing runtime sources and their required static dependencies. Ensure neither target resolves the other's API through accidental duplicate static state.
6. Update normal/lite distribution archives, signing manifests and required-file validation to include the matched pair. Update client and WinVM test deployment/restoration to save, install and restore both files. Update install/rollback docs to require both files and explain pair/version mismatch diagnostics.
7. Move detailed crash-recovery tests with the runtime. Add a child-process fault test proving the shim writes a structurally valid minidump through `BugSplat_createReport` with `nevr.dll` absent and after runtime load/API/init failure; prove normal runtime crash instrumentation remains active with a compatible `nevr.dll`. Exercise diagnostic path fallback, unwritable destination, full disk/write failure, and a second crash while reporting, ensuring the process does not recurse or deadlock.
8. Run `just configure && just build`, then `just verify`. Run focused PE contract and loader-state tests under Wine. Run `./launch-client.sh` on `Xephyr :101` with `WAYLAND_DISPLAY` unset; verify a rendered window and successful login using the game's own log. Separately exercise missing and incompatible runtime with a non-production harness, and exercise the external launcher ABI path. Run dedicated-server smoke coverage if its configured local test environment is available.
9. After any commit touching runtime code, run the required nested client login test and report exact commit/test evidence. No release, tag, deployment, or Nakama operation is part of this goal.

## Current verification state

Step 1 (PE contract and ABI descriptor):

- `tools/verify_pe_contract.py` runs in `just verify` against the built `BugSplat64.dll`: the export name set must equal the 26 names above, `DetoursExportPlaceholder` must be ordinal 1, and the host must not import `nevr.dll`. With the game binary present it also requires echovr.exe's nine `BugSplat64.dll` imports to be by name, equal to the pinned set, and exported. PE export tables carry no types for the undecorated C exports, so signatures and calling conventions are not covered by this check.
- `src/core/runtime_abi.h` defines the v1 descriptor (16-byte header `struct_size`/`abi_major`/`abi_minor`/`reserved`; `NevrHostContext` carrying the game module and the host-owned `PreprocessCommandLine` trampoline; `NevrRuntimeApi` with `initialize`, `preprocess_before`, `preprocess_after`) and header-only validators. `test_runtime_abi` (11 GTests, Wine) covers rejecting a major mismatch in either direction, a short struct, or a missing entry, and accepting a newer minor or a larger struct. It also covers never reading past a short descriptor, using a guard-page case. An over-reading validator faults that test.

Step 2 (attach-time MinHook proof gate), under Wine only:

- The probe host (`src/runtime/tests/bootstrap_attach/host_probe.cpp`, built as `BugSplat64.dll`) does what the proposed attach path does: it runs the production `GameImageGuard` (timestamp `0x6452dff6`), validates the 18-byte prologue at RVA `0x116720`, computes the sibling `nevr.dll` path into a fixed buffer, and installs one MinHook detour, all from `DLL_PROCESS_ATTACH`. Nothing else happens in attach. The test executable supplies an image whose `PreprocessCommandLine` begins with the real 18 echovr.exe bytes, so MinHook relocates and executes the real prologue.
- Scenarios, each in its own child process: valid; missing runtime; ABI major mismatch; missing entry point; init failure after the runtime patched something; invalid PE; 8 threads making the first call while init is slow; a thread calling the target across the whole attach; the same with DllMain held open for 100 ms after the hook is live; same-thread re-entry during runtime init; wrong timestamp; wrong prologue. A second executable imports the host statically, as echovr.exe does. It proves attach completes before `main` and that `nevr.dll` is not loaded at `main` entry.
- Each child checks the following from a timestamped event log. Attach steps run in order. No runtime load, `DllMain`, API, init or dispatch happens before attach exit. Every issued call runs the original exactly once, with the exact argument and result. Per-thread before -> original -> after nesting is balanced. Failures degrade to original-only calls. The runtime's own MinHook copy hooks a disjoint target alongside the host's.
- Mutation checks, each of which fails the suite: loading `nevr.dll` inside DllMain; calling the original twice; removing the same-thread re-entry bypass (the child deadlocks and times out).
- Findings that bind the real host: (1) a same-thread re-entry during runtime load must bypass to the original, because `InitOnceExecuteOnce` recursion on the loading thread deadlocks (measured); (2) the trampoline and host context must be published before `MH_EnableHook`, because a racing thread entered the detour before `MH_EnableHook` returned (observed); (3) attach failures must return TRUE and leave the game unhooked, because the game imports the host statically.
- Not yet proven: native Windows (the doc requires both). `tools/winvm/systest.py` has no scenario that runs this harness, and `WINVM_USER`/`WINVM_PASS` were unset when this ran. The Windows parallel loader's worker threads, which MinHook freezes during attach, are not exercised under Wine. The nested client run that confirms ordering in the real game is also outstanding. Do not move runtime sources until the native Windows run passes.

## Acceptance criteria

- The built shim exports all 26 current replacement symbols with exact names, ordinals, signatures and calling conventions; no eager import of `nevr.dll`; all current public NEVR/plugin entry points remain available through the host.
- The stable host and runtime have independently visible PE version information and compatible build identity/API version.
- The host emits a useful diagnostic on each runtime load/API/init failure and never calls an absent function pointer. Echo VR's own BugSplat/dump imports still resolve.
- A deliberate game crash that reaches `BugSplat_createReport` before the first Preprocess rendezvous, without `nevr.dll`, and after runtime load/API/init failure, produces a structurally valid host-owned minidump in the first writable configured destination; with a compatible runtime, detailed crash instrumentation still produces its expected evidence.
- A compatible runtime reaches the early hooks once, preserves original call behavior, renders the client window and reaches logged-in state in the required nested-display run.
- Normal and lite packages, install/rollback docs, test deploy/restore scripts and signing inventory all include the matched `BugSplat64.dll` + `nevr.dll` pair.
- `just verify` passes after implementation; no release/deployment or Nakama change occurs.

## Main risks to review

- Whether `PreprocessCommandLine` is a sufficiently early and loader-unlocked rendezvous for both client and dedicated-server startup.
- How the bootstrap host and runtime share or isolate MinHook state while the host owns the one early detour.
- Whether every current replacement export has a caller that needs a stable host wrapper; retain the complete current 26-symbol export set initially and use call-site/package evidence to classify each implementation.
- Crash-safe callback correctness if dump writing occurs while the process is faulting; output-directory permission failures; and preserving the before/original/after server bootstrap ordering. Faults that bypass the game callback require a separately designed and tested fallback before being claimed as covered.
- Preserving game image-base/render behavior and avoiding double initialization across direct and launcher paths.
- Updating every distribution/test/installation path so a matched pair cannot silently become a one-file install.
