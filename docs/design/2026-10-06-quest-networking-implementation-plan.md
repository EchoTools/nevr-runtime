# Quest networking implementation: shared source, measured callbacks

Date: 2026-10-06
Status: Astra approved preparation tranche 0 and bounded implementation tranche 1a; later tranches require separate review

## Scope and existing baseline

Quest and PCVR clients use the same game-facing EVR behavior. The work is to reuse the PCVR policy, login data, wire handling and session routing in both builds, with narrow PE/ELF, game ABI and OS adapters. The first seam is the **same logical config-string lookup** that PCVR already hooks; an Android HTTP request hook is not yet established. No Quest-specific framing, protobuf matchmaking frames, local Nakama, game configuration mutation, routine game launch, APK install, headset, or production-service check belongs to these tranches.

Current `HEAD` is `918d4c9`. Tranche 1 of the older plan was completed in `4b11c98`: `src/runtime/compat/login_profile.cpp` is compiled by the Windows runtime, `test_behavioral`, and Android `nevr_quest_login_profile` (`src/runtime/CMakeLists.txt:33,588`; `src/quest/CMakeLists.txt:30-35`). The Android profile target is not linked into the sentinel. The current sentinel is `entry.cpp` plus `got_hook.cpp`; `HookImport` has no detach or duplicate guard and ignores the last `mprotect` result (`src/quest/sentinel/CMakeLists.txt:5-9`, `got_hook.cpp:127-136`). The Android preset already uses the Quest-local vcpkg manifest, `arm64-android`, NDK chainload and API 26 (`src/quest/CMakePresets.json:7-17`); the older design's contrary setup step is stale.

The present host has `adb` at `/opt/android-sdk/platform-tools/adb` and `qemu-system-aarch64`, but no `emulator` executable or arm64 Android system image was found in `/opt/android-sdk` or `/home/andrew/Android/Sdk`; the latter contains an x86_64 Android Wear image. Thus an arm64 Bionic runner is **not currently available**. Provisioning it is a prerequisite, not an assumed test result. Plan capacity for one isolated VM runner with at least 4 GiB RAM and 10 GiB free disk (planning allocation, not a measured package size); measure actual image size, boot time and test duration before setting CI deadlines. Prefer an arm64 Android VM image at API 26 or newer; the existing x86_64 Wear image and Linux `qemu-aarch64` do not satisfy Bionic/arm64 loader tests. Preflight must record ABI/API, Bionic linker/libc, and successful execution of an NDK arm64 probe DSO plus `mprotect`/`dlopen` smoke. Do not install packages or launch a VM in this design pass.

`docs/design/2026-10-06-quest-testing-regime.md` supplies the offline test gates. This plan supersedes the implementation sequence and routine-run assumptions in `docs/design/2026-10-06-quest-networking-port.md:59-67,103-136`; its binary and EVR source evidence remains useful.

## Promotion and evidence gates

1. **No guessed ABI:** opaque Quest CJson layout and C-string return are handled without reading or modifying game fields; a typed declaration follows callsite registers and return flow. Any need to inspect game fields, any different flag width or any hidden ABI parameter requires new exact-binary evidence. Test an exact-ELF caller path under arm64 Bionic if static evidence leaves return ownership or call entry ambiguous. A synthetic callback alone is insufficient.
2. **No unsafe hook lifecycle:** fixture hash/build ID and relocation must match before write. One handle owns one module slot and its captured, actually resolved pointer; its address need not equal the owning ELF's local definition. Confirm Bionic lazy binding does not recurse; check `mprotect` restore and exact pointer restoration on production detach. Retained replacement strings survive detach/DSO unload because storage is intentionally process-lifetime. Do not turn on the game hook if thread/frequency, loader timing, original pointer stability or teardown safety affects correctness and remains unmeasured.
3. **Same source, no drift:** Windows and Quest CMake targets name the same portable `service_redirect`, stable pool, login profile, eventual codec and router files. Each new portable source has direct Windows and Android test linkage; Win32/MinHook, Bionic/GOT, file search, TLS and game-object types remain adapters. Existing `src/core/hooking.h:35-109` has reusable publish-before-enable behavior but Windows headers; extract only its portable lifecycle contract when doing so reduces duplication, keeping MinHook and GOT mechanics separate.
4. **Offline acceptance only here:** use exact-build fixture tests, MinGW/Wine unit tests, NDK artifact checks and a *provisioned* arm64 Bionic VM for OS-specific behavior. The VM is unavailable today, so those checks are blocked until its preflight passes. No routine device installation, game process, production account, config edit, local Nakama, or production log is required or authorized by this plan. A later release qualification for exact installed APK identity and actual game invocation is separate. No implementation, build or test was performed in this design pass.

**Process gate before a runtime-code commit:** `AGENTS.md` §“System test after every commit” requires `./launch-client.sh` against production after runtime commits, while the current user scope bars routine game/runtime/service checks. This document cannot amend or waive `AGENTS.md`. Offline preparation can finish, but before Luna makes a runtime-code commit the owner must correct `AGENTS.md` or explicitly settle which current rule governs. No such run is authorized in this design pass.
