# Quest controller hand flip: placement in the VrApi layer, with a menu toggle (the layer is design; the sentinel interim is built)

Tracking issues: #1986 (the report), #2007 (the placement), #2043 (moving the interim roll into the layer). The measurement that decides whether this is built is in this tree (`src/quest/sentinel/hand_pose_log_hook.h`, smoke row Q34 in `docs/testing/smoke-checklist.md`). This document is the design that follows only if that log shows the roll the prediction names. The fix belongs to the VrApi-on-OpenXR layer (Placement). The only fix this tree can make while that layer is not reconstructed here is the sentinel interim, which is marked known-wrong below.

## Condition
Build it only if the two logs (Touch and Touch Pro or Touch Plus, same Quest 2, same pose) show a relative rotation of 180 degrees (170 to 190) about the controller's local Z axis, with the axis within 15 degrees of Z. Otherwise the logged quaternions decide the transform and this design changes. The gate applies to the layer's key and to the interim alike.

## What the game does
Disassembly of libr15 (pinned build `b243509c08ce677aeb95fa348016949b3fc45230`; the disassembly VA is the pinned VA + 0x100000). `CVR::PollTracking` (0x1a7142c) calls `FUN 0x1a71808`: enumerate the input devices (call 0x1a71840), `vrapi_GetInputTrackingState` twice per device (0x1a718c4 and 0x1a718dc), and for type 4 only the capabilities (0x1a718fc). The hand is `!((ControllerCapabilities >> 2) & 1)`. The pose goes unchanged into the hand's slot (stride 0x68). `PollTracking` then applies one tracking-space quaternion (reset to identity by `CVR::Shutdown`, 0x1a6f128) equally to the head and both hands. Nothing depends on the controller model, so a roll comes from the pose VrApi reports for that controller.

## Placement

### The layer owns the fix
Controller differences belong in the VrApi-on-OpenXR layer: the code that answers the game's `vrapi_GetInputTrackingState` and `vrapi_GetInputDeviceCapabilities` for its controllers. ADR 0033 (controllers are mapped by OpenXR interaction profile inside the VrApi layer) rule 1 puts them there, with pose corrections keyed by the path `xrGetCurrentInteractionProfile` reports. Its rule 2 keeps code above the boundary from branching on the controller to change input.

If #1737 brings the layer into this repo's scope, it is reconstructed here (ADR 0033 rule 3, ADR 0035), with EchoFrame and Ducky's reference combat build cited as references and never taken whole (AGENTS.md, Guardrails). The reconstruction takes its facts from the reference binary's disassembly and the OpenXR specification, its lines follow `docs/standards/logging.md`, and its tests fail when the change is reverted.

The layer is not in this tree. The release base carries the reference build's `libvrapi.so` (`tools/quest_release_base.py` names it), and `tools/quest_runtime_pin.py` and `tools/quest_repack_libs.py` pin its output into the signed APK. This repo therefore changes no code in the layer. ADR 0035 makes the layer class 2 once it is reconstructed here.

The scope is open. #1737 row G6A-094 marks the VrApi-on-OpenXR runtime out of scope for this repo's own code; the release APK carries the reference build's runtime as it is (above), which this repo neither builds nor changes. ADR 0033 and ADR 0035 say how the layer is made if #1737 brings it into scope; they do not bring it in. This design does not settle that, and no layer work is scheduled until the scope is settled (#1737).

### The key: the interaction profile
The layer reads `xrGetCurrentInteractionProfile` for each hand's top-level user path, `/user/hand/left` and `/user/hand/right`. For a hand whose profile is one the measurement below shows flips, the layer applies the roll to the orientation it returns for that hand's tracked-remote device: `q' = q * (0, 0, 1, 0) = (y, -x, w, -z)` for `q = (x, y, z, w)`, the same roll as the interim. Position, velocities, status and times stay as written. Other profiles, hand tracking and unknown devices are not touched.

The key names no headset. #1737 row G6A-096 describes the reference build's default table (Quest 2 none, Quest 3 a 180 degree roll). That table is keyed on the headset, and ADR 0031 and ADR 0032 do not allow a headset-keyed fix, so it is not the key here.

### The measurement that decides the key
Measurement A decides the key when it separates the two controllers. On one Quest 2, record the profile path the layer reports for `/user/hand/left` and `/user/hand/right` with Touch, then with Touch Pro or Touch Plus, one session each. If the paths differ, the key is the path of the flipped controller. The path strings are not stated here: whether Touch Pro and Touch Plus report distinct paths on a Quest 2 is not measured (ADR 0033, Not claimed).

Measurement B applies only when A does not separate them. It keys on the grip-to-aim relative rotation of the same hand, from the grip and aim spaces the layer locates for it. If the Touch and the Touch Pro or Touch Plus logs differ in that quantity by the Condition's amount (170 to 190 degrees about the controller's local Z axis, axis within 15 degrees of Z), the key is that relation, and the roll applies only where the measured relation shows the flipped pose. If B does not separate them either, the layer has no automatic key: no layer fix is built, and the interim is the only control.

Both measurements come from one line per bound controller per session, which the layer writes (ADR 0033 rule 4): the profile path and the pose source. Whether the roll was applied and the grip and aim orientations are this design's own fields, beyond ADR 0033 rule 4. The line's tag and fields follow `docs/standards/logging.md` and `docs/standards/naming.md`.

The current logs cannot decide the key. The `hand_flip_device` line (`src/quest/sentinel/hand_pose_log_hook.cpp`) has no profile field, and no code in this tree calls `xrGetCurrentInteractionProfile` or locates a grip or aim space. Whether the reference build's own log names the profile path is not checked.

### The menu toggle beside Texture Resolution
The toggle is the player's switch for the interim while the fix is not verified on a headset (#1986). It has no effect on the layer's key. Because it exists only for the unverified interim, its row, its file and the interim's log lines are dropped in the change that moves the fix into the layer.

- Menu: `texture_menu.cpp` `WalkMenu` keeps the `graphics|msaa` row alone on a page renamed NEVR; it becomes a list of two rows, Texture Resolution and "Controller Hand Flip", a NAMED FLAG (`value` true is Off, the default; `truestr` "Off", `falsestr` "On"), because a STRING ARRAY writes an integer the game refuses in the boolean setting. `WalkGameSettings` removes any quest hiding entry for the new row's path.
- Carrier field: `graphics|fullscreen`, `SR15GfxSettings` flags bit 0 (offset 0, mask 1; `src/quest/sentinel/hand_flip.h`). A Quest has no fullscreen mode, and the settings struct is at `CR15Game+0x8dc8`. The game's own value of the bit is 1: the v6.16.4 headset log prints `Fullscreen: Enabled` at every start (39 lines, none `Disabled`; `ApplyRuntimeGfxSettings` prints it from `flags & 1`). So Off is the bit set, which is the game's value, and On is the bit cleared (`BitFor`, `FlipFor`): a player who never turns the toggle on leaves the bit as the game holds it, and the first delivery writes it only when the game held it clear (logged once as `hand_flip_carrier before=<0|1> after=<0|1>`). The settings writer saves the bit (`InspectFlagBit`'s write form), so the bit's value is what the game saves. Consumer audit of the pinned libr15 (ReVault binary 576, VAs the pinned VA + 0x100000; the instruction search covered 1 of 1,041 binaries, the Quest library only): 14 sites form the struct's address (`mov w, #0x8dc8`), in 13 functions: `ConfigureEngine`, `LoadSettings`, `InitEngine` (two), `SaveSettings`, `SettingsJson`, `UpdateSettings`, `WriteGameSettingsAsJson`, `InitCI`, `UpdateExclusiveWriteSettings`, `WriteSettingsToUI` and `Initialize` of `CR15SettingsTranslatorCS`, and the `CR15GfxSettingsExpression` call operator and its `BindExpression`. Read in full: `ReadGfxSettingsFromJson` and its `Inspect` (`InspectFlagBit` accepts a boolean or an integer and never fails, 0x13cf3b4), `ValidateGfxSettings` (touches no flag), `ApplyInitialGfxSettings` and `AutoPickGfxSettings` (read no flag), `ApplyRuntimeGfxSettings` (reads bit 0 only for its `Fullscreen:` log line), `WriteUIToSettings` and the expression. The expression copies the struct into a script thread and exposes `flags & 1` as a boolean output named `fullscreen` (the symbol `CSymbol64("fullscreen")`, 0xbe467be7dcbb8352); whether any script data reads that output is not checkable in the binaries. The other sites were read by name and callees only (the settings file's load and save, the translator's UI sync). `+0x04` (the fallback) is the setting `display` (echovr.exe `fcn.140c2e8c0`, and the Quest script binding by hash), copied by the same expression; it is a display setting the scripts may read in a way nothing here can rule out, so no row is bound to it.
- Live apply: `HandleApply` (`texture_menu_hook.cpp`) sees every delivery. Read the field; the first delivery is the stored choice or the default. ## Tests
Interim unit tests: the roll (`(y, -x, w, -z)`; applied twice gives `-q`); only type 4 rolled; flag off leaves the bytes identical, on changes only the four orientation floats; both polls of a frame rolled; menu rewrite (second row after Texture Resolution, shape mismatch, texture rows unchanged); start resolver (no file means off and nothing written, a menu change writes the versioned file, unversioned and other-version files ignored); live apply with no restart; golden log lines; pinned slots; static-initializer and code-page-write scans. Each fails when the hook is reverted.

Layer tests, when the layer is built: the key on the path, with one flipped and one unflipped profile (the flipped hand's orientation rolls, the other hand's bytes are identical); the roll applied twice gives the negated quaternion; hand tracking and unknown devices untouched; measurement B's rule rolls only in the measured relation; the per-controller line golden. Each fails when the roll is reverted.

## Headset
Interim, Quest 2 with Touch Pro or Touch Plus, toggle Off then On from the menu without a restart: the hands are palm-correct on the next frame with On; a restart logs `hand_flip_start source=player_marker flip=1`; the game's own `Fullscreen: Enabled` line while the toggle is Off and `Fullscreen: Disabled` while it is On; Quest 2 with Touch controllers and the toggle Off is unchanged.

Layer, when built, Quest 2 with Touch Pro or Touch Plus and no toggle: the per-controller line names the flipped profile for each hand, and the hands are palm-correct from the first frame. Quest 2 with Touch controllers: the line names the Touch profile and the hands are unchanged.

## Not verified
