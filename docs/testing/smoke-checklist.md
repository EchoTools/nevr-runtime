# Smoke-test checklist

One row per feature a tester can check on a PC game client, a Quest game client or a game server, with the player action that exercises it and the log line that proves it. The proof column cites the source file that writes the line; `just verify` checks the file paths in this document.

## How to use

1. Sync the clock first. Every tester syncs the device clock (PC: Windows time sync; Quest: automatic time on) before the run, so PC and Quest log timestamps can be lined up afterwards.
2. One tester per platform. One person drives the PC game client, one drives the Quest. Rows that involve another player (friends, party, voice) need two real game clients; say who the second tester was in the notes.
3. Walk an area top to bottom. For each row do the player action in "Smoke test", then find the line in "Proof": PC logs are `%LOCALAPPDATA%\nevr\echovr\logs\nevr-<timestamp>.jsonl` (the earliest boot lines are also in `nevr-boot.jsonl` in `logs\` of the game folder); Quest logs are logcat tag `NEVR-Sentinel` and `nevr-sentinel.log` in the game's external files folder.
4. Tick the box only when you saw the action work and found the line. Paste the line into the notes. A line that appears while the action visibly failed is a fail: leave it unticked and note it.
5. "Log-only" means no player action reaches the row; the cell says how to trigger or read it. "Absent" means the game has no UI for it.
6. Platform: PC means the Windows or Wine game client; Quest means the Android sentinel; both means the same row applies to each (test it on each).

`TP#n` is row n of [`docs/design/2026-10-01-social-features-test-plan.md`](../design/2026-10-01-social-features-test-plan.md), the social test plan. Config keys live in `config.yaml` (PC, [`docs/reference/example-config.yaml`](../reference/example-config.yaml)) or in the same `config.yaml` on the Quest (the app's files folder, `src/quest/sentinel/quest_config.cpp`). Open problems with a feature are tracked in the [issue tracker](https://github.com/EchoTools/nevr-runtime/issues).

## Game server mode

Operator rows: run on a dedicated game server (`echovr_server.exe` or `echovr.exe -server -headless -no-console`). Nothing here is reachable by a player in the UI, so each row says how to trigger it.

A dedicated game server begins multiplayer after its login ([#45](https://github.com/EchoTools/nevr-runtime/issues/45)): its log shows `[NEVR.PATCH] server logged in — beginning multiplayer`, then `Beginning multiplayer` and the bring-up the rows from SV07 on check. After the login, `Beginning multiplayer` appears once. A second one about ten seconds later, with no new login before it, is the double begin row B28 describes: it is followed by `HTTP API listener failed to bind` and `ForceFatalExit(62)`. The state machine also queues a begin at any later `logging in -> logged in` switch (a re-login); what that begin does on a running server is not verified. At boot it first logs `[NEVR.PATCH] server bring-up prologues validated`; a changed prologue of either game function ends the process with `[NEVR.FATAL] server bring-up: ... prologue mismatch`, and so does a net game that is not logged in when the begin runs.
